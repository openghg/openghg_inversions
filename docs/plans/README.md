# Planning records and validation evidence

Repository plans retain delivery history, proposals, research, and validation evidence. They do not define current capability requirements, architecture policy, priorities, or release gates.

- [RHIME development principles](../development/rhime_model_development.rst) explain readable scientific composition and ownership.
- [Numerical array ownership](../development/numerical_array_ownership.rst) explains borrowing, sparse payloads, and explicit execution boundaries.
- [Capability specifications](../../openspec/specs/) and [OpenSpec changes](../../openspec/changes/) are the homes for reviewed behavioral requirements and proposals. Check their review and delivery status; a proposed requirement is not a claim of implemented support.
- GitHub issues own outstanding implementation and acceptance tasks. A research candidate or historical checklist does not authorize new work or establish that a feature is supported.
- [User documentation](../usage/usage.rst) describes the supported package. Plans may mention interfaces that have changed or proposals that have not merged.

## Extraction boundaries

Delivered behavior belongs in documentation; a proposed behavioral change belongs in a reviewed capability change; remaining implementation or acceptance work belongs in an owning issue. Preserve scientific assumptions and evidence when extracting explanation. Do not promote experimental cache layouts, superseded compiler designs, or uncalibrated benchmark recommendations into requirements.

The numerical ownership investigation retains its Zarr-cache hypothesis as research. The W1 map retains PR #590's characterization history; several listed node names were later removed or renamed, so it is not a current test inventory. The model-family and programme roadmaps retain dated status claims; implementation and issue evidence must be checked before migrating their contents.
