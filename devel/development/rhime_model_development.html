Developing RHIME models#

RHIME is maintained for atmospheric scientists who need to read, adapt, and cite the model code. Its development principles favour code locality and a visible scientific narrative over a generic model framework.

The target style is a procedural shell with a concept-oriented functional core. The useful quality of the release-0.6 fixedbasisMCMC workflow was that a scientist could inspect one imperative recipe and then follow plainly named scientific functions. Preserve that reading experience without restoring the old monolithic function, mutable dictionaries, parallel-list state, or implicit **kwargs forwarding.

This page gives design and review guidance. Exact supported arguments, errors, compatibility periods, and artifact guarantees belong to their scoped capability specifications and usage references. See Development guidance and behavioral specifications for those sources and how to establish their review and delivery status. A design recommendation is not evidence that an API implements it.

Keep legacy dependencies one-way#

The HBMCMC isolation and retirement contract defines normal execution through supported modern interfaces without migration translation. Modern behavior must have modern owners; normal execution must not invoke migration tooling. Canonical configuration rejects unsupported options before scientific work, including every explicit use_tracer occurrence.

PR 869 delivered the earlier one-way isolation boundary. The current #719 branch removes the transitional namespace and adapters; completed revision-specific checks are recorded in the active change’s tasks and PR #974. Specification synchronization and archival remain separate closeout work. The development migration guide records removed interfaces and replacements. See Development guidance and behavioral specifications for capability ownership and the scientific amendments on this branch.

Start with the scientific recipe#

Read a recipe as a scientific pipeline with optional checkpoints: acquire, prepare, build, sample, reconstruct, and write products. The runner makes the sequence visible; a saved-stage entry point resumes supported operations from a declared handoff. The pipeline and checkpoint architecture explains these responsibilities. A prepared-input recipe need only implement the entry points and products it actually supports.

The core principles for new RHIME work are:

  • Keep top-level orchestration procedural and readable from top to bottom.

  • Construct the concrete model in mathematical and scientific order.

  • Use scientifically meaningful names, explicit inputs, and ordinary callable components. Configuration is a convenience for selecting resolved values.

  • Accept small duplication when it keeps alternative scientific recipes clear. Within one recipe, full and saved routes call the same step functions with the same objects; a saved route only loads a checkpoint before and saves one after.

  • Use dataclasses for concrete scientific concepts or durable handoffs.

  • Normalize configuration at its owning boundary and forward named values explicitly, including an explicit config.data.select("name", ...) selection where useful.

  • Keep helpers close to their scientific owner. Tiny registries can serve homogeneous families such as filters without controlling the whole model.

  • Make local modification possible: a scientist can copy a runner or replace one component without reconstructing a framework lifecycle.

The review test is:

A scientist familiar with release-0.6 fixedbasisMCMC can read a runner, open one nearby concrete model function, and replace one ordinary component whose interface explains what RHIME supplies.

Preparation helpers should own an operation, policy, meaningful handoff, or necessary compatibility boundary. A uniform stage name, timing, or argument renaming alone does not justify a second forwarding signature. Keep shared indexing reusable and model-specific preparation policy beside its recipe. Call canonical prepare_basis directly with resolved arguments and use the actual sensitivity, selection and assembly implementations. Do not retain forwarding wrappers solely for uniform stage names, timing or keyword translation. Pass per-site datasets and aligned SiteOptions between preparation steps; acquired MergedData remains separate. Construct results from their scientific inputs rather than modifying the result after construction. Use Architecture principles and recipe boundaries to assess responsibilities and consumer interfaces, and Validation and labelled-array patterns to identify validation owners.

Choose the smallest useful extension#

A named model recipe combines a procedural runner with a readable concrete model builder. It may reuse preparation, numerical, sampling, and output functions while keeping their scientific composition visible.

Use these questions when extending RHIME:

  1. Can an existing component accept the option while preparation, state sharing, observation channels, and output meaning remain the same?

  2. Does a change to those structures deserve a named recipe with its own assumptions and tests? Similar short orchestration is acceptable.

  3. Do two production recipes use the same equations and option meanings? Extract that demonstrated shared component.

  4. Is this still a project-specific experiment? An ordinary callable extension point can provide a useful incubation path.

  5. Is a variant recurring in papers? A tested in-tree recipe lets the released package version and DOI identify its implementation.

Reconsider a general registry or framework only after real recipes show stable repeated structure. A public recipe should have an obvious runner and builder, a runnable example, equation tests and a smoke test, and documentation of its inputs, outputs, assumptions, limitations, and scientific citation.

For current public selection and names, use RHIME terminology and prepared-input reference and Running RHIME from the command line, backed by the model-selection contract. Selection dispatches to concrete recipes; their input contracts can differ. The Standard RHIME model family, Nested-domain model family, and CO₂ model family pages describe implemented family support.

Compose scientific concepts directly#

A component represents a concept used when discussing the model: basis functions, a flux contribution, a baseline, pollution events, model-data mismatch, aggregation error, or a likelihood. It need not be mathematically atomic. A baseline can combine boundary conditions, an offset, and fixed outer fluxes; a multisector component can combine several pollution contributions.

Prefer a normal function. Its name, options, inputs, and result should explain the scientific concept. A composite can call nearby smaller functions; keep a model-specific composite beside its recipe until another production recipe uses the same equations and meanings. Semantic graphs and manifests are unnecessary prerequisites for authoring a component.

Some components have alternatives that share a lifecycle: options resolved before any data, bound to one fit’s data, added to a model, and declared for saved outputs. Represent each alternative as small frozen dataclasses behind structural protocols, as the boundary families do; a recipe then calls the same methods whichever alternative it receives. A shared base class is appropriate when alternatives handle their data identically. Keep each alternative’s recipe in its own add: the base provides the steps, not the order.

Return the smallest result the consumer needs. An observed tensor can be the whole result of a likelihood. A small dataclass can join related scientific outputs, such as aligned observation channels or a coherent reduction. A shorter signature, speculative flexibility, or provenance alone does not justify a new domain object.

Recipes represent concentration contributions with ConcentrationTerm: absolute output, likelihood contribution, and an optional fixed observation shift. Compose these explicitly with likelihood_representation so a numerical reference is restored exactly once. See Boundary-condition operators for the scientific equations.

For a concrete likelihood, show the completed mean and how measurement error, fixed aggregation error, and inferred mismatch enter its probability model. These quantities have different scientific meanings; the supported covariance representations belong to the concrete likelihood and recipe. Do not infer universal support from a common calling signature. Current equations and restrictions are explained in RHIME terminology and prepared-input reference and CO₂ model recipes.

Sampler choice becomes part of the recipe when the graph and update algorithm are coupled, for example through a state-likelihood cache or an ordered CompoundStep. Keep the graph, sampler, and update order together. An ordinary likelihood variation can use the existing callable seam without a new runner or a general sampler protocol. Fixed OU, IID site sigma, and global sigma are different scientific targets even when they reuse numerical kernels. Use a stock PyMC calculation as the correctness reference for an optimized route.

Build model graphs from array operations. A Python loop or sum over a fixed handful of terms unrolls into a few graph nodes and is fine; prefer one n-ary pt.add to a chain. A loop whose length grows with the data, such as one per site, period or state, belongs in a matrix product or a concatenation, as the per-period boundary mean shift uses an indicator matrix rather than one term per period.

Preserve labels until a named numerical boundary. Shared alignment values such as SigmaAlignment keep site/period interpretation close to the mismatch component; repeated factorization or parallel lists can hide that meaning. The model-composition contract owns the registered coordinate and standard/multisector custom-likelihood interfaces. Follow Customising RHIME for a concrete replacement example. Covariance axes still need their own scientific alignment; registering one dimension does not establish that an independently supplied matrix has the right second axis.

Keep positive-support prior policy beside prior construction rather than repeating distribution allow-lists in each likelihood. Validate independently sourced values at the boundary that owns them, then trust locally constructed intermediates. Ordinary labelled alignment, Pint conversion, and the numerical operation itself often express the required check; add a custom assertion when it protects a scientific policy or gives a materially better boundary failure.

Boundary component extension check#

A boundary family is a choice, one resolved selection of the user’s options before binding, and a bound record, both small frozen dataclasses in one module under models/boundary/. The configuration adapter resolves user options such as bc_freq and bc_prior into a choice (MultiplicativeChoice or AdditiveChoice); it never touches arrays. Runners take that one choice (a channel mapping for linked recipes) and bind it once per channel and fit through bind_prepared, which dispatches on the representation preparation recorded: choice.bind(observations, sensitivity) for a RawCenteredSensitivity Dataset, or choice.bind_absolute(observations, H_bc) for absolute H_bc, which only the multiplicative family implements. Either returns the bound record, which pairs the choice with borrowed labelled sensitivity on the fit’s rows and boundary periods; its data carries the sensitivity contract (BoundCenteredSensitivity for centered families). The runner passes the materialized bound record, not the choice, to the numerical builder. Reusable raw sensitivity keeps its spatial meaning independently of fit periods. The same options, choice and bound sequence suits other components whose options define a prior over data-dependent states.

Recipes materialize the bound record with their other inputs in one dask.compute over to_dense_tree(), which traverses dataclasses, including prior parameters in the choice. For example, after binding the boundary and selecting the model inputs:

from dask import compute
from openghg_inversions.array_ops import to_dense_tree

inputs, boundary, priors = compute(
    *to_dense_tree((inputs, boundary, priors))
)

Keep this computation joint: a boundary-only materialization method could execute sensitivity graphs again when the other model inputs use them. The eager check in boundary.add enforces the materialized-data precondition. Inside the registered model, boundary.add(...) returns an AffineConcentrationTerm, a ConcentrationTerm subclass: ordinary recipes use it as a term, and cached recipes lower its labelled AffineBlock designs and physical coefficients once into numerical matrices. sampled_rvs identifies the underlying sampled variables, including transformed priors. boundary.outputs() declares the roles, units and metadata recorded with the trace. A linked recipe embeds native rows and namespaces coordinates without recovering boundary-family equations. Offsets remain separate components; the offset-confounding warning inspects every affine block for a constant unit response, so it needs no knowledge of boundary families.

The centered families inherit CenteredBoundary: add registers the sensitivity, adds the family’s corrections in scientific order and finishes the term with the shared helpers, while outputs extends the shared declarations. The additive recipe composes its mean shift, anomalies and complete boundary concentration in that order, and passes their summed state correction through M once. Factor construction and sampling share the same selection of contrast basis or direct state sampling.

The scalar bc_anomaly_scale saved in model data records the resolved prior width for trace reconstruction; the distributions use the resolved choice value directly. Likewise bc_scale_sd records anomaly-scaling provenance. Updating these saved scalars does not update the distributions’ widths.

Validation is not repeated along this path. Preparation and artifact loading own units, labels and layout; bind owns calendar and row alignment and the single float64 check for centered sensitivity; add checks only values that become available once lazy payloads are materialized.

A new supported boundary prior reaches these owners:

  • A new module under models/boundary/: define the choice (with bind) and the bound record (with add and outputs), inheriting CenteredBoundary for a centered family. Choice and Bound are structural protocols, so no shared list of families changes.

  • rhime/co2/configuration.py and, for channel-specific syntax, co2_o2_configuration.py: resolve user selections into component inputs.

  • Scientific component tests and the affected configuration tests: establish the equation, fixed-state behavior, units, full density and gradients.

The cached conversion aligns only observation rows; it does not align separate coefficient axes. Unsampled additive anomalies are registered as zero model data, so replay reads every declared role from the saved draws or constants.

For a new family, scientific tests belong with its component in tests/models/test_boundary_components.py and its configuration in tests/test_rhime_co2_configuration.py or tests/test_co2_o2_configuration.py. The generic embedding and replay probes in tests/test_co2_boundary_affine_integration.py, tests/test_boundary_output.py and tests/test_co2_bound_frontends.py protect the consumer seam; downstream boundary-family work supplies the new prior’s equation tests. The boundary-library adoption record preserves the builder-signature counts and extension probes from that migration.

The review check is that this module list does not grow to include likelihood, cache, sampler or output modules. Those consumers operate on the shared affine result and the component’s declarations through the existing OutputContract. The pure saved-boundary decoder/reconstructor reads fitted scientific facts, including the constant zero anomalies of mean-only fits, from saved draws and constants. Prior and posterior groups retain independent sample sizes; replay neither builds a graph nor chooses a new period calendar.

Keep configuration with its scientific owner#

Treat configuration as a description of scientific choices. Group those choices by the component that owns them: for example, boundary family, reference, periods, and physical widths; flux and prior choices and their calibration; or offsets and likelihood choices. Resolve and normalize each choice once at the boundary that owns it, such as configuration parsing, preparation, or model construction. Later stages should consume explicitly resolved values without implicitly reselecting a model or recalibrating its inputs.

Runtime inputs and user choices are different interfaces. Function signatures describe observations, sensitivities, priors, and existing model terms. Configuration groups choices by the component that owns their meaning. For example, boundary-condition prior and period choices belong to the baseline; site/period mismatch choices belong to the error model.

Keep accepted options and defaults beside those consumers. Compose them explicitly at resolution rather than inferring a schema from every runtime argument or introducing a generic option registry. Let each file frontend own its syntax, apply raw overrides before normalization, and forward resolved values explicitly. A moderately long keyword-only signature can be clearer than an ambient context object or implicit forwarding through the pipeline.

The current standard/multisector requests are described in Advanced RHIME configuration. That reference and the reviewed configuration change own requested choices and their resolution. Canonical prepared construction belongs to the scientific-input contract; persisted formats and replay belong to the prepared/sample handoff contracts. The request precedes preparation; retained-site execution facts become known later. Frozen records do not imply recursive immutability of borrowed arrays or caller-owned containers.

Configuration groups acquisition and preparation choices under RhimeConfig.data: DataConfig. The runner acquires data separately and passes it into scientific preparation. MergedData holds acquired data only; preparation steps pass per-site datasets and SiteOptions between them. Standard and multisector recipes support reusable preparation and sample manifests; see Staged RHIME workflows. The remaining family adoption tasks from PR 802 remain active. This guide does not fix private module locations, configuration class layout, or future manifest structure. Existing templates and complete option listings belong with their recipes and usage references.

Preserve scientific handoffs and output meaning#

Prepared inputs join labelled, backend-neutral scientific products. A recipe selects the arrays it consumes and materializes related values together at the named model boundary. Extension or diagnostic variables need not become model inputs merely because they share a Dataset. A scientifically distinct recipe can compose reusable prepared values without pretending to be substitutable for another family.

Moving a preparation equation, including observation-error derivation, minimum-error calculation, or boundary-period expansion, is a scientific change requiring evidence for unchanged behavior and explicit tests for agreed semantic changes. Model-owned minimum-error estimates use retained observations after invalid-row removal; historical pre-drop estimates are not a parity target. Observation-error imputation follows selection filters and uses only retained observations. These numerical rules belong to the scientific-inputs contract; configuration owns the accepted choices and phase resolution. Supported prepared-input contents and examples are in RHIME terminology and prepared-input reference and Customising RHIME; checkpoint limitations are in Staged RHIME workflows.

Standard and multisector preparation retains raw spatial BC inputs and operands for supported minimum-error choices. A compatible later model can change BC periods or floor policy without repeating spatial preparation. Saved samples retain the fitted alignment and floor operands; replay consumes those exact values without a new graph or calculation. The active prepared handoff contract and sampled handoff contract own those artifact guarantees. CO2’s prior-dependent coherent preparations retain their separate reuse constraints. The #876 alignment change tasks record revision-specific validation evidence and limits. Broader handoff programme acceptance remains pending.

Internal Python APIs, staged manifests and prepared/posterior artifacts have no compatibility guarantee; only CLI behaviour and CLI outputs are protected. Do not add readers, aliases or shims for earlier internal formats. Reject old artifacts with instructions to prepare again. The approved boundary-label change uses interval-start timestamps in CLI products.

Keep one scientific sample codec owner for save/load and let replay consume its decoded result. Keep product/export saving in a nearby operational helper with shared naming/path policy, and normalize descriptive sampler provenance through a shared pure metadata operation. These are development recommendations; the behavioral contracts require scientific parity and artifact meaning without fixing internal helper names or call graphs.

Source selection and state grouping should remain plainly named operations on labelled values and retained artifacts. Resolutions, partitions, sources, and observation channels need explicit labels. Variable suffixes or positions alone cannot preserve those scientific meanings.

Record each declared quantity where its values vary. A pm.Deterministic is saved with every draw, so use it for quantities that depend on sampled variables. A quantity that is fixed for the fit, such as the boundary reference or zero anomalies that are not sampled, belongs in model data (constant_data), stored once. Keep its role either way, so output readers need no policy, and broadcast constants over the draws where they are read. This is not a ban on deterministics: selecting which sampled deterministics to record is a separate choice.

Postprocessing needs quantity meaning as well as arrays. Small scientific-role mappings can connect a model’s local names to real output consumers without imposing a compiler or backend naming convention. Define the quantity, units, dimensions, and uncertainty scope with the output contract. The maintained Linear retained-state reconstruction and Affine native-flux reconstruction pages explain current reconstruction and its limits; their reviewed capability changes are linked from Development guidance and behavioral specifications. A role name alone does not promise a storage schema or graph-free replay for every analysis.

The numerical ownership rules apply throughout: inputs are borrowed and may be Dask-backed; copying, computation, densification, persistence, and serialization belong at visible boundaries. See Numerical array ownership and execution for the reasoning and Validation and labelled-array patterns for practical patterns.

Record evidence and scientific ownership#

Public recipe documentation should cite accessible scientific sources. Implementation-history paths and private commit hashes belong in issues, pull requests, or internal parity records. Released code, examples, and tests should remain understandable without private Verification Games access.

OpenGHG Inversions owns released reusable components and production recipes; Verification Games owns calibration cases, experimental orchestration, campaign configuration, and independent acceptance evidence. A cutover includes the downstream consumer and removal of its duplicate implementation after parity, as well as merging the package implementation. Track that acceptance work in the owning issue rather than treating a historical plan as completion.
